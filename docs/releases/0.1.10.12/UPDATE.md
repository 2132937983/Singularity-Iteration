# 0.1.10.12 更新说明：反应堆事故调查与电网分配饥饿修复

基于 0.1.10.11（`pr-0.1.10.11-20261019`）。共 2 项。构建环境为 Gradle 8.10.2、JDK 21、NeoForge 21.1.218，离线构建。

## 1. 反应堆事故调查命令与诊断界面

### 黑匣子（飞行记录器）

* 每台核反应堆发电机在内存中记录最近 40 个反应周期（40 秒），每个周期一条：
  * 外壳热量（周期前、周期后、上限）、产热、散热片排出的热量、进料倍率带来的额外外壳热量、EU/t；
  * 列数（反应仓）、相邻位置中未加载区块的数量、开关状态；
  * 流体模式：低温／高温冷却液、容量、转换量；发电机模式的液体冷却：预算、用量、低温／高温冷却液；
  * 储热元件的热量与容量、燃料棒与冷却元件的数量、本周期熔毁与耗尽的元件、掉出的元件、自动化放入／取出的物品数。
* 同时保存最后一个周期的 54 个槽位（物品、种类、热量或损耗、剩余燃料、枯竭标记、未建造的列），以及窗口期内熔毁的元件（槽位、熔毁前的状态、时间）。
* 记录器只在内存中，不写入方块存档；世界加载后重新开始记录。

### 事故记录

* 下列情况会把黑匣子保存为一起事故（主世界存档数据 `mio_icif_reactor_incidents`，保留最近 64 起）：
  * 核爆炸；
  * 反应堆局部爆炸；
  * 配置关闭了反应堆爆炸、外壳热量达到上限（此时不会爆炸；每次过热记录一次，外壳降到 90 % 以下后重新计数）；
  * 运行中或外壳热量不低于 10 % 的反应堆被拆除。
* 每起事故包含：编号、类型、现实时间、游戏时间与天数、维度与坐标、所有者（放置反应堆的玩家）、事故时 64 格内的玩家、爆炸强度、模式、进料倍率、外壳热量、黑匣子数据与原因分析。服务器日志写一行摘要。
* 爆炸之后，现场掉落“反应堆黑匣子”（`mio_icif:reactor/item_reactor_blackbox`）：不会烧毁、能承受爆炸、发光、永不消失，带有事故编号与主因。使用（右键）即打开报告；持有者都可以阅读。

### 原因分析

第一项为主因（红色），其余为次要因素：

| 代码 | 主因／因素 | 判断依据 |
|---|---|---|
| `removed` | 运行中或高温时被拆除 | 拆除记录 |
| `chunk_boundary` | 反应仓位于未加载的区块 | 列数减少且相邻区块未加载 |
| `chamber_lost` | 反应仓丢失 | 列数减少（附掉落元件数） |
| `grid_blast` | 外部过电压（机器爆炸） | 窗口期内 16 格内有接收端因过电压爆炸 |
| `coolant_hot_full` | 高温冷却液储罐已满：排热停止 | 流体模式，高温储罐已满且没有转换 |
| `coolant_empty` | 冷却液耗尽 | 流体模式，低温冷却液为 0 |
| `liquid_cooling_lost` | 液体冷却停止 | 发电机模式，液体冷却从有效变为 0（冷却液用尽或高温冷却液未取出） |
| `sudden` | 热量骤升 | 一个周期内从 50 % 以下升到上限 |
| `heat_runaway` | 热失控：冷却不足 | 外壳热量连续上升至少 3 个周期（附平均产热与散热） |
| `component_melted` | 冷却元件熔毁导致热失控 | 窗口期内有散热片、冷却单元、热交换器等熔毁（附种类与数量） |
| `fuel_added`、`feed_rate`、`automation`、`component_saturation` | 运行中添加燃料、高进料倍率、自动化搬运物品、储热元件 90 % 以上 | 次要因素 |
| `unknown` | 原因不明 | 没有周期数据 |

* 热失控与元件熔毁同时出现时：外壳先连续上升 5 个周期以上，判为冷却不足（熔毁是结果）；否则判为元件熔毁。
* 分析是纯计算（`ReactorAccidentAnalyzer`），结果随事故一起保存。

### 命令

* `/mio_icif reactor audit`：事故列表（从新到旧，最多 20 行）：编号、时间、维度与坐标、类型、主因；点击一行打开报告。
* `/mio_icif reactor audit <编号>`：打开该事故的报告；控制台得到文字摘要。
* `/mio_icif reactor audit clear`：清空记录（权限等级 2）。
* 管理员可以查看全部事故；普通玩家可以查看自己反应堆的事故，以及自己在 64 格内时发生的事故。

### 调查报告界面

* 标题栏：事故编号、类型标记、日期时间、游戏天数、维度、坐标；所有者与附近的玩家。
* 结论框：主因（红色粗体）与说明、建议；下方为次要因素。
* 堆芯布局：最后一个周期的 54 个槽位。熔毁的元件显示在原位置（红色并打叉），耗尽的中子反射板为橙色，枯竭燃料为灰色；槽位下方的条表示元件热量（绿→红）或燃料棒剩余燃料；未建造的列为暗色。鼠标指向显示物品、种类、热量／燃料／损耗与熔毁时间。
* 热量曲线：最近 40 秒的外壳热量（红线，虚线为上限）与每周期的产热（橙）／散热（蓝）柱；鼠标指向显示每个周期的数值、熔毁、自动化与列数变化。
* 指标：最后一个周期的外壳 %、产热与散热、EU/t、进料倍率、列数、冷却液、燃料棒、冷却元件饱和度、自动化次数。

### 指南

* 新页面“反应堆事故调查”（三种语言），核反应堆发电机页新增“事故调查”一节。

## 2. 大功率设备独占电力导致普通机器断电（饥饿）

### 原因

* 报告的电网：太阳能 → 储电 A → 物质生成机、复制机、512 变压器（模式存储器／扫描仪）；主线经储电 B → 分子重组仪，分子重组仪另有一条直连太阳能的旁路；太阳能 → 储电 C、D → 水平母线 → 7 台普通机器。
* 公平模式按阶段分配：先负载与变压器（类别 0），后储电设备（类别 1）；同一阶段内，每台设备得到相同的“需求满足比例”。
* 分子重组仪是类别 0 的负载，剩余空间 1.2 亿 EU，额定输入没有上限。按比例分配时，它几乎拿走太阳能的全部输出。储电 C、D 是类别 1，要等所有负载都满足之后才充电；分子重组仪很久都不会充满，所以 C、D 一直拿不到电，后面的 7 台机器断电。在母线末端单独加太阳能能恢复，正是因为那是不经过 C、D 的电源。
* 第二个问题：每个 tick 的接收端窗口（每个窗口最多 128 个接收端）总是从同一个接收端开始，后面的窗口只能分到前面剩下的电。
* 预留（报价）与实际消耗：每个电源的每 tick 额度在 tick 开始时冻结，按实际扣除结算，没有发现因预留未消耗而锁死的情况。

### 修复

1. 最大最小公平（注水）分配：同一阶段内每台设备得到 `min(需求, 水位)`，水位是预算能支付的最高值。需求小的设备先被完全满足，剩下的电由需求大的设备平分。分子重组仪仍能拿到水位以上的剩余电量，但不能再占用其他设备的份额。
2. 中继需求：向下游机器供电的储电设备，在第一阶段与负载一起请求一 tick 的输出量（数据包大小 × 包数，减去自身储量能提供的部分，且不超过额定输入）。不向任何设备供电的储电设备照旧在负载之后充电（`FairGridGameTests.loadsBeforeStorage` 不变）。
3. 窗口轮换：接收端多于 128 个时，每个 tick 的第一个窗口从上一 tick 停下的位置之后开始，长母线上的接收端轮流分配。

### 验证（离线测试 `Harness1112`，26 项全部通过）

按报告的电网建模（太阳能 3,000 EU/t，第 1000～1999 tick 的平均值）：

| 分配器 | 7 台普通机器 | 分子重组仪 | 物质生成机 | 复制机 | 扫描仪 |
|---|---|---|---|---|---|
| 0.1.10.11 | 0 EU/t（全部停机） | 3,000 | 0 | 0 | 0 |
| 0.1.10.12 | 224 EU/t（全部运行） | 1,735 | 347 | 347 | 347 |
| 0.1.10.12，窗口倒序 | 224 EU/t（全部运行） | 1,735 | 347 | 347 | 347 |

* 太阳能只有 300 EU/t 时：母线得到其平均份额 150 EU/t（0.1.10.11 为 0）。
* 同一电源上的小负载与分子重组仪：0.1.10.11 时 LV 机器约 0.0003 EU/t，现在为 32 EU/t（其余给分子重组仪）。
* 旧的数值检查（verify-si181 的 1～9）、中继需求 4 项、随机不变量（预算、空间、守恒、无损、电压上限）与最大最小性质各 3,000 组，全部通过。

### 行为变化

* 同一阶段内“每台设备相同的需求满足比例”不再成立：需求不同的设备，需求小的先被满足。需求相同的设备仍得到相同的电量。
* 配置 `energyNet.distributionMode` 与 `core.ini` 的说明已更新。
