# 0.1.11.0 更新说明与游戏内测试清单：电网岛局部更新（阶段 1）

基于 0.1.10.44。电网性能与互通提案（2026-11-02 审计，Q1–Q12 全部按推荐方案批准）的阶段 1：岛局部更新与拓扑管理分离。

| 项目 | 内容 |
|---|---|
| 岛与版本（P-3） | 导线的连通分量（岛）有自己的版本：编辑只结束它触及的岛，其他岛的路由视图、路由计划、空闲记忆与路径档案保持有效 |
| 受影响端点（P-9） | 编辑后暂停的端点只在被触及的岛旁查找，不再扫描该维度的所有端点 |
| 单一导线索引（P-8） | 平台拓扑读取引擎的导线索引，不再保存第二个索引（及其从不清空的编辑记录） |
| 补结算（C-1，修正） | 编辑后的补结算在暂停那一 tick 的帧内进行，不再损失一个 tick 的输送 |
| 计划缓存 | 缓存满时丢弃最近两个 tick 未使用的最旧计划 |
| 外部 FE 发现 | 锚点的增减只探测新锚点的六个邻居，不再启动完整扫描 |

改动在工作区中，未提交。能量规则不变（C-1 是修正：0.1.10.44 每次暂停都会少输送一个 tick）。没有新增配置，存档格式不变。本文按项目列出改动，每节后附游戏内测试步骤与预期结果。

---

## 0. 测试准备

- **世界**：创造模式，开启作弊（`/mio_icif perf` 需要权限等级 2）。
- **配置**：使用默认配置（独立电网，线损默认 `LOSSLESS`）。
- **诊断指令 `/mio_icif perf`**：每个维度一行，包括电网结算的中位、p95、最大值（ms）与“路由计划 新建 / 续用 / 预算用尽”；另有“FE 每 tick”的邻居探测次数。
- **两个电网**：第 1、2 节需要同一维度中互不相连的两个电网：
  - **大电网 A**：例如用 `/fill ~ ~ ~ ~63 ~ ~31 mio_icif:wiring/cable/block_tin_cable_1` 铺 2,048 根线缆，四周放若干发电机与机器（或储电箱）。
  - **小电网 B**：在 A 旁边（不相连）放一台发电机、3 根线缆、一台储电箱。

## 1. 岛局部更新（P-3、P-9）

### 改动（`ConductorRegistry.java`、`ReceiverContacts.java`、`IndependentSiEnergy.java`）

- **岛**：`ConductorRegistry` 的连通分量称为岛。编辑（放置、破坏、改变面）立即结束它触及的岛；没有被触及的岛在之后的快照中保持相同的标识、顶点 ID 与路径搜索。顶点 ID 按岛分配，岛有效期间不变（ID 之间有空隙，范围用尽时全部重新编号）。
- **路由代数**：只在端点出现、消失或改变面时增加。0.1.10.44 中，每次导线编辑使代数增加 3 次（暂停、补结算、下一次完整结算），每次都让整个维度的路由计划重新构建。
- **按岛保留的缓存**：
  - 每个缓存的路由计划保存其起点所在岛的印记（`IslandStamp`）。印记中的岛都未变时，计划在新快照上继续使用。
  - 空闲记忆、路径档案与导体信息也按岛保留。
  - 暂停与补结算使用自己的空缓存（`RoutingCaches`），不再清空完整结算的缓存。
- **受影响端点（P-9）**：编辑后暂停的端点（`affectedEndpoints`）只在被触及的岛的导线旁查找；导线比端点多时，与 0.1.10.44 一样检查全部端点。多格发射端（`IEnergyEmissionSource`，或发射位置不是自身位置的端点）仍全部检查。

### 测试

1. 电网 A 与 B 都在送电、没有编辑时，间隔 20 秒执行两次 `/mio_icif perf`，记下该维度“路由计划 新建”（自启动以来的累计）的增量。
2. 在 B 上反复放置一根相连的线缆再破坏它（约每秒一次，持续 20 秒），前后各执行一次 `/mio_icif perf`。**预期**：“新建”的增量与第 1 步相近（0.1.10.44：每次编辑都让该维度的全部计划重新构建，增量随编辑次数明显增大）；结算中位与不编辑时相近。
3. 在 A 上做同样的编辑。**预期**：A 的计划重新构建（“新建”的增量变大），编辑后的下一 tick 恢复送电；B 的送电不受影响。
4. 普通电网（发电机、线缆、机器、储电箱、变压器、保护线缆）：送电、熔断、变压与 0.1.10.44 相同。

## 2. 补结算（C-1，修正）

### 改动（`FeLedger.java`、`IndependentSiEnergy.java`）

- **0.1.10.44**：编辑附近的端点在 tick 结束（END）时暂停，在下一 tick 开始（START）时补结算。补结算使用下一 tick 的每 tick 额度（源的输出、机器的输入），这一 tick 的 END 就没有额度了：每次暂停少输送一个 tick（源保留 EU）。
- **0.1.11.0**：补结算在暂停那一 tick 的帧内运行，使用暂停那一 tick 的额度（新增 `FeLedger.inFrame`：FE 账本按指定 tick 的额度计算；不允许嵌套）。下一 tick 的 END 保留自己的额度。
- **搜索与路由额度**仍按服务器 tick 计算：补结算与同一服务器 tick 的结算共用，一个服务器 tick 的工作上限不变。

### 测试

1. 一台发电机经 3 根线缆连接一个储电箱（例如 BatBox），储电箱足够大、开始时为空。等待 30 秒，记下储电箱的电量增量。
2. 清空储电箱，在接下来的 30 秒中，每 2 秒在这 3 根线缆旁放置一根相连的线缆，再破坏它（每次都编辑同一个岛）。**预期**：电量增量与第 1 步相同（0.1.10.44：每次编辑少输送一个 tick 的电量，30 次编辑约少 30 tick；这部分留在发电机里，发电机存满后不再发电）。
3. FE 机器（其他模组）同样测试（可选）。**预期**：FE 的输入与输出不超过每 tick 的额定值。

## 3. 单一导线索引（P-8）

### 改动（`PlatformTopology.java`、`IndependentSiEnergy.java`）

- `PlatformTopology.Observer` 新增 `keepsConductorIndex()`（默认 `false`）与 `conductorIndex(ServerLevel)`（默认 `null`）。SI 引擎返回 `true` 与自身的索引；拓扑只按区块保存导线位置（容量检查用），`snapshot` / `isCurrent` 读取引擎的索引。
- 0.1.10.44 的拓扑还保存一个第二索引：没有任何代码读取，已编辑位置的集合从不清空（放置并移除 100,000 根线缆后占 43 MB）。16,000 根导线时拓扑现在占 234 KB（原 7,378 KB）。
- 拓扑的快照来自引擎的索引：引擎在发布该 tick 时才应用采样的条目，因此可能比采样晚一个 tick（产品代码中没有调用者，只有测试使用）。

### 测试

1. 用 `/fill` 放置约 100,000 根线缆（分几次），再全部清除；重复 3 次。**预期**：F3 中的内存在 GC 后回到接近开始时的水平（0.1.10.44：每轮约增加 43 MB 且不释放）。
2. 线缆的区块容量检查：在一个区块中放置大量线缆，超出上限时的提示与 0.1.10.44 相同。

## 4. 计划缓存与外部 FE 发现

### 改动（`IndependentSiEnergy.java`）

- **计划缓存**：缓存（64 个计划）满时，按插入顺序丢弃本 tick 与上一 tick 都未使用的计划，再缓存新计划。0.1.10.44 在缓存满后不再缓存新计划，编辑后的旧计划一直占满缓存。
- **外部 FE 发现**：添加或移除锚点（导线或机器）不再启动完整发现扫描（0.1.10.44：每次锚点编辑都重新探测该维度的所有锚点，并忘记之前的未命中）。新锚点的六个邻居在下一次结算中探测；排队超过 16,384 个位置（例如区块加载）时仍执行一次完整扫描。

### 测试

1. 在电网 A 的末端延长一根线缆，并在新线缆旁放置其他模组的 FE 电池。**预期**：1 秒内开始充电。
2. 反复放置与破坏 A 的线缆时观察 `/mio_icif perf` 的“邻居探测”。**预期**：每 tick 的探测次数与不编辑时接近（0.1.10.44：编辑期间大幅增加）。

## 6. 与提案的差异

- **edit_local_16k 未达到 < 1%**：最终代码的 4 次运行中供给减少 1.5–3.9%（0.1.10.44：4.7–5.0%；1k 与 4k 为 0%）。补结算本身足额输送（30,720 EU）。之后的结束结算发现基准的接收端已满：每个接收端存 1,024 EU，基准每 tick 在结束结算之后清空一次，128 个窗口中 124 个没有空间，一次结算 128 批的上限在 4,096 EU 处结束这一轮。这是基准接收端的容量造成的；批数上限未改（阶段 1 不改变行为）。
- **edit_far_16k**：与不编辑的 far_16k 之差在波动之内（之比 1.03–1.06，0.1.10.44 为 1.02–1.06），16k 电网的结算时间本身占主导。
- **`LongIntMap` 位置索引未采用**：`Harness1150` 测得 16k 岛编辑后的快照重建平均 10.47 ms（最好 7.58 ms），其中约三分之二是 HashMap 查询；但一次结算的位置查询只需约 0.30 ms（16,000 次，每次 19 ns）。只减少重建中的查询（不换索引）已使重建平均 11.56 → 10.39 ms（−10%）。换成 `LongIntMap` 留到阶段 3（L1 的 SoA 收支计算会重写这些结构）。
- **`ContactOrder` 保留自己的记录**：提案要求 `PlatformTopology` 与 `ContactOrder` 都读取引擎的索引（P-8）。`ContactOrder` 记录的是放置顺序（legacy 分配的平局排序），引擎的导线索引没有这个信息，因此只改了 `PlatformTopology`。
- **补结算的额度（C-1）**：最初按结算帧重置搜索与路由额度，补结算的 tick 因此有两份额度：500 个源的压力 GameTest 不再用尽额度而失败，edit_local_16k 也没有改善（交替比较：按帧 30,197 / 29,897，按服务器 tick 29,527 / 29,821 EU/t）。最终只有 FE 账本使用暂停那一 tick 的帧，搜索与路由额度仍按服务器 tick。
- **计划缓存的代价**：周期长于缓存容量的 comb_4k 失去命中（每 tick 0.29–0.53 次 → 0），每 tick 构建的计划 7.5–7.7 → 8.0，分配 +2–4%。换来 edit_far_4k 的计划 38.9 → 19.6（与满后保留的策略比较）。
- **分配**：没有编辑的 16k 场景在交替运行中 +1–2%（far_16k 27,820 / 26,621 → 28,293 / 27,058 KB/tick，计划数相同；0.1.10.44 自身在不同运行之间为 26,212–27,820）。关闭逃逸分析时 29,035 → 29,772（+2.5%）。来源未能定位，结算时间在波动之内。
- **未采用的试验**：范围结算保存并恢复完整结算的源与接收端游标。edit_far_4k 的计划 19.5 → 17.2，但补结算刚填满的接收端在下一次结束结算中又被选中：edit_far_16k 的入账 30,703 / 30,687 → 30,247 / 30,199 EU/t，edit_far_1k 1.17 / 1.27 → 1.62 / 1.67 ms。
- **拓扑的快照**：在引擎维护索引的模式下，`PlatformTopology.snapshot` 返回引擎的索引，可能比采样晚一个 tick（产品代码没有调用者）。
